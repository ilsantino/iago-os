## 4. [Critical] src/lib/report-supervisores.ts

replayChains (lines ~387-400) under-counts supervisor chain occurrences on same-timestamp clear+start replay. Events sort clear (rank 0) before start (rank 1) at an equal timestamp, and a chain only opens when `open === false`. For the shape `escalado 10:00 · clear 10:00 · escalado 12:00`, the 10:00 clear is consumed while nothing is open, the 10:00 start sets `open = true`, and the 12:00 re-escalation is skipped entirely — `starts = [10:00]`, so `chainStats.chains` reports 1 where truth is 2, and accept/clear outcomes can attach to the wrong occurrence. These are printed as headline supervisor-chain stats in the client-facing PDF. This is not speculative: the in-code comment at lines 433-438 states the defect verbatim ('consumes that clear while nothing is open, and leaves `open === true` forever — so the 12:00 re-escalation never becomes a second start and `chains` under-counts too') and explicitly declares the repair 'deliberately NOT attempted here'. The paired `neverCleared` over-report is pinned by a test, but the `chains` under-count is not. Fix: give the replay an event identity/order key so a same-instant clear closes the intended occurrence without blocking subsequent starts; regression test the clear+start-at-T1 then start-at-T2 shape.
