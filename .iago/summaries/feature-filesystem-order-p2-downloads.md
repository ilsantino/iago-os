### 11 corrected — a real tool finding

`extract_entity` returns the **first** vocabulary token in the filename, not the most specific one. Where two tokens appear, it picked wrong:

| file | tool said | corrected to |
|---|---|---|
| `LISTA DE PERSONAL Y TURNOS MES DE JUNIO.xlsx` (×2) | `personal` | `sentria` |
| `~$Sentria-Personal-Junio-ABSARA.xlsx` | `personal` | `sentria` |
| `iaGO_RedSunFarms_*` (×4), `iaGO_RSF_Calculadora_*` | `iago` | `rsf` |
| `propuesta-iago-fimunet.*` (×3) | `iago` | `munet` |

The Spanish `personal` case is the sharp one: *personal* means **staff**, and "LISTA DE PERSONAL Y TURNOS" is a Sentria roster, not a private file. It also corrupted the descriptor — the entity token is consumed, leaving `lista-de-y-turnos-mes-de-junio`. Corrected, it reads `lista-de-personal-y-turnos-mes-de-junio`.

Because `is_conforming()` is checked **before** hints are consulted, an already-renamed file cannot be re-owned by a later scan. That is why batch 1 was rolled back and re-run rather than patched — and the rollback doubled as a live proof of the undo path.

**Recommended fix (P1 follow-up, not done here):** prefer the client/project token over `iago`/`personal` when several match — e.g. score by specificity, or let a path/sibling signal break the tie.
